# ADR-0026: The issuance claim is the record, and every absent token names its reason

**Status:** Proposed · **Date:** 2026-09-18 · **Deciders:** Tech lead, Security lead · **Relates to:** ADR-0008, ADR-0015, ADR-0016 · **Origin:** increment-2 `D-4` and `D-5`

## Context

Three defects on the mint path, and they are related closely enough that fixing one without the others leaves the fix incomplete.

**`D-5`, the wedge.** `TokenService.issue` claimed the decision in the `IssuanceLedger` *before* the pipeline wrote the `token_issued` record. If that write failed the token was correctly withheld — and the claim stood. `InMemoryIssuanceLedger` never purges, deliberately. So that `decision_id` became **un-mintable forever**, reported as `HARNESS_UNHEALTHY`, which is an infrastructure reason and therefore terminal and non-escalatable: no human could unstick it. One transient outage in a one-call window poisoned a decision permanently, and there was no test of retry-after-outage.

The obvious fix is refused *in writing* by the code it would change. `tokens/nonce.py`: *"An issuance has no such backstop: forgetting it is indistinguishable from never having minted, so a purge would re-open the second-mint path the moment the first token expired — and a second mint is a fresh token with a fresh lifetime, which is the whole defect."* That argument is correct. And "provably never returned" is unprovable in the failure mode that matters: on a crash between claim and write the compensating release never runs, and on a store timeout the record may in fact have landed.

**`D-4`, the outcome that lied.** `EvaluationOutcome(verdict=ALLOW, token=None, evidence_failed=False)` was constructible, and every issuance failure after the evaluation record landed produced exactly it. The defence was a docstring saying every consumer reads `permits_execution`. The consumer is the gateway, written in a later increment.

**The `HARNESS_UNHEALTHY` misfiling.** A duplicate-issuance refusal is a control working correctly. Declaring an infrastructure reason made an operator dashboard and the `NFR-21` correlated-failure alert read it as the harness being ill.

**And a fourth, which only surfaced because of the others.** The write-ahead log stages whatever the store could not take and replays it on recovery. For a `token_issued` record whose token was withheld that is wrong twice: the chain would assert an authorisation that never existed, and — once the record's identity is derived from the decision — the replay would then refuse every retry of a decision that was never authorised at all.

## Decision

1. **The claim is the record (`D-5`, option (c)).** `issuance_record_id(tenant_id, decision_id)` derives the `token_issued` record's `record_id` as a `uuid5` of the decision. The evidence store already refuses a second record with an id its chain holds, so **that refusal is the at-most-once conditional insert**, and "has this decision ever been authorised?" is one `has_record` lookup rather than a scan. `TokenService.issue` gains one keyword, `issuance_evidence`; without it the old two-step path is byte-for-byte unchanged.

   This answers the never-purge argument rather than working around it. Nothing is released and nothing is purged, so the docstring's reasoning survives intact — but there is no longer anything to forget: an entry exists **iff** the record landed, and the thing that must never be forgotten is now the append-only record, which cannot be forgotten by construction. The question the docstring called unprovable is not asked: a failed write leaves no claim, and whether it landed is answered on the retry by *reading the chain*, not by guessing.

2. **Un-staging is permitted for exactly one record (the fourth defect).** `_drop_staged_issuance` discards the staged `token_issued` record, named by its derived id, only after its own write failed. The pipeline may do this precisely because it can prove the token never left the method. It never touches the evaluation record, which stays staged and replays exactly as `FR-23` requires. This is the narrowest exception that makes item 1 correct, and it is recorded here because the agent that implemented it correctly observed that it was a decision with no ADR.

3. **Every absent token names its reason (`D-4`).** `EvaluationOutcome.withheld: TokenWithheld | None`, with a construction-time invariant: `token is None` **if and only if** `withheld` says why. Stated as a biconditional rather than two checks because the gap between them was the defect. `evidence_failed` becomes a property derived from `withheld`, so the two cannot disagree, and keeps exactly the meaning it had: *the evaluation record did not land*.

   The invariant is stated over the *token*, not over `verdict.permits_execution`, because a shadow class holds a token on a `DENY` (`INV-11`) — the verdict is the wrong predicate. The token is the only signal that anything may execute, so the token is what the invariant is about.

4. **`DUPLICATE_ISSUANCE:<decision_id>` replaces `HARNESS_UNHEALTHY`** for a refused second mint. It is **not** in `INFRASTRUCTURE_REASONS`, so a working control stops being filed as an outage. Non-escalation — which is the property that actually mattered — does not come from that set; it comes from not being in `ESCALATABLE_REASONS`, the allowlist for a class's `escalate_on`. So no human can wave a second mint through, which is right: nobody can vouch for authorising one decision twice. Subjected with the decision the chain already authorises, which is the first thing an operator looks for.

## Alternatives considered

- **`D-5` option (a): a compensating release confined to provable absence.** Not implementable as `§3.4` framed it, and the plan attached `has_record` to the wrong option. `EvidenceWriter.write` mints the `record_id` internally, so a caller compensating after a failure has no id to look up; `has_record` only becomes usable once the identity is *derived*, which is option (c). Option (a) would need a chain scan or a change to `evidence/`. It also cannot handle a writer that commits and then raises.
- **`D-5` option (b): keep the never-purge and add an operator recovery path.** Rejected: it leaves the wedge in place and makes a human the compensating mechanism, on a path where the human's only available action is to authorise a second mint — the one thing the ledger exists to prevent.
- **`D-4`: set a flag on both paths, or demote the verdict on both.** Both are narrower fixes to the same shape and both leave the type able to represent the bad state; the next path added would have to remember. A discriminated reason makes it unrepresentable and, as a side effect, tells a caller *which* failure it was, which the flag could not.
- **Keep `HARNESS_UNHEALTHY` and change nothing.** Rejected: it is the `T-06` confusion the round-two review already fixed once at the class level, and it costs twice — the real outages are diluted, and the control looks like a defect.

## Consequences

- **Positive.** A decision whose issuance record failed is mintable again, with the retry test that was missing. A second mint is impossible in *more* cases than before, including a writer that commits then raises and a read replica whose `has_record` lags its writes — where the derived id makes the append itself an independent second line of defence. An evidence outage on the mint path now reports `EVIDENCE_UNAVAILABLE`, which a retry can clear, so **every remaining `DUPLICATE_ISSUANCE` provably names a decision the chain already authorises**. `pipeline/decision.py` and `tokens/nonce.py` reach 100% line and branch coverage.
- **Negative, and it is a behaviour change nobody asked for.** Because the record's identity is derived, a **replay (`FR-71`) of a recorded decision can no longer mint a spendable token** — the append collides. This is almost certainly correct and strictly safer, but it is a consequence of the mechanism rather than an intended feature, and anyone building the replay harness (`P1-16`) needs to know it before they design around it.
- **Negative, retention moves.** The ledger has no retention policy of its own any more. What governs at-most-once minting is now the decision-record retention, `DEFAULT_RECORD_RETENTION_DAYS` (400 days, `NFR-16`) — four orders of magnitude longer than the token lifetime the purge argument was actually about. No new constant was introduced, and that is the point: the ledger stopped being a thing with a lifetime of its own.
- **Negative, a contract change.** `EvaluationOutcome` gains a required-in-practice field. It is keyword-defaulted, so positional construction is unaffected, but an existing caller constructing one with `token=None` now raises. Two test fixtures did exactly that and were building the bad state; both are fixed. `evidence_failed` changes from a field to a property, which is source-compatible for readers and breaking for anyone who passed it — nothing outside the pipeline did.
- **Follow-up.** `DecisionToken.decision_id` is a bounded `str` while `DecisionTokenRecord.decision_id` is a `UUID`, so the token layer still accepts decision ids the record layer refuses — the same divergence `ADR-0025` closed between the resolver and the record catalogue, one layer over. Surfaced by this work (a test fixture used `dec-0001`) and **not fixed here**: narrowing the token model is a separate change with its own blast radius.
